# Goal
A proven system's vertical and horizontal shape becomes a model the plugin applies to any similar project, the owner approving every decision it seeds ([Models](../design/models.md), [0020](../decisions/0020-architecture-models-are-data.md)).

# Bolts
## B228 The model format
- AC-1 A model folder (`model.json`, `knowledge/`, `decisions/`) loads from `plugin/cli/models/` and `.aidlc/models/`, the local one winning; `aidlc check` reports a model that breaks the format.
## B229 The modelling pathway
- AC-1 A `model` pathway intent needs its `research:` digests and a current Model doc (`aidlc models doc <name>`, generated from `model.json` with its digest), else `PATHWAY-SKIP`; the owner approves the Model doc.
- AC-2 Each layer, domain and rule of a project model cites a source of those digests, else `MODEL-SOURCE`.
## B230 Rule types
- AC-1 Stage order, slice contract, long-running operations, idempotency, data and events are rule types the model sets with parameters; each is off unless the chosen model sets it.
## B231 Applying a model
- AC-1 Greenfield: intake proposes the models whose fit matches; choosing one writes the system doc, the proposed decisions and increments along its layers.
- AC-2 Brownfield: the codebase map's modules are matched to the model's layers and kinds, and the gaps are listed as increments.
## B232 The control-plane model
- AC-1 The control-plane model ships under `plugin/cli/models/control-plane/` in generic names, built through the modelling pathway; a scan finds no vendor name in it.
## B233 Reference slices
- AC-1 The Go pack carries the control-plane model's reference slices, tested; a second, minimal model applies with no change to the core.
## B234 The architect's model knowledge
- AC-1 The architect persona knows how to read a reference horizontally and vertically and how to write its rules as data, within its budget.
