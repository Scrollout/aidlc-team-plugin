# Goal
Inception produces a coherent design that a human has really validated, as AI-DLC intends.

Unchecked, it goes wrong in three ways:
- Decisions are approved in bulk, faster than anyone can read them.
- Decisions contradict each other, such as a quota transaction across domains, or a rule that layers own no data beside a schema a layer owns.
- Platform facts, such as the cluster's identity form and certificates, are assumed, not probed.

# Bolts
## B173 Pathways
AI-DLC has the AI pick the stages each intent needs ([Grid](../design/grid.md)).
- AC-1 An intent declares `pathway: greenfield|feature|brownfield|defect`, approved with it, and `next` runs exactly that pathway's steps. A skipped step is `PATHWAY-SKIP`.
- AC-2 `brownfield` starts with reverse engineering (R0): the codebase map written and a kind for every module (`upgrade` proposes them). Legacy names and boundary violations as a baseline decision are the migration intent's own work in [M21](m21.md).
## B174 A sized intent, real answers
- AC-1 `INTENT-SIZE`: at most 5 increments and 5 domains, with success measures per increment.
- AC-2 Each question in `# Questions` offers options with consequences. An open question is `ELAB-OPEN`; an answer that names no option is `ELAB-BARE`.
## B175 Domain docs and the context map
- AC-1 A domain doc per domain the intent touches, holding:
  - code, kind, owned tables;
  - surface (commands, queries, events);
  - relationships with their pattern;
  - glossary.
- AC-2 The context map is generated from them. A requirement in no domain is `DOMAIN-REQ`, data owned twice is `DOMAIN-DATA`, and one term with two meanings is `DOMAIN-TERM`.
## B176 Platform facts
- AC-1 `aidlc fact "<title>" --env <environment> -- <command>` runs a read-only probe on the target and records the command, environment, output digest, date and output as a Fact doc; a probe that fails records nothing.
- AC-2 A decision whose `affects.platform` cites no fact is `FACT-MISSING`; one older than the profile's limit is `FACT-STALE`.
## B177 Structured decisions within a horizon
Decisions amended in place to match the code lose what was decided and why.
- AC-1 A decision declares `affects`, `oneWayDoor`, `supersedes` and `facts`. An approved decision can't be edited (`DOC-AMEND`); a change is a superseding decision, with `reason: code-first` when code came first.
- AC-2 `DECISION-HORIZON`: a draft decision whose `serves` names only increments beyond the next two of its intent.
## B178 The coherence check
- AC-1 `DESIGN-COHERENCE` reports:
  - a transaction across two domains' data;
  - a dependency against the kind matrix;
  - data owned twice;
  - a horizontal module owning write data;
  - an unsuperseded contradiction on the same `affects` key.
- AC-2 A quota transaction across domains and a layer owning data against a no-data rule are fixtures it reports.
## B179 The design review
- AC-1 Before the owner approves the decision set, the reviewer runs an architecture focus over the whole set and records it with `aidlc review record I-<n>`. A CONFIRMED finding blocks approval of the intent and its one-way doors until the owner runs `aidlc dispose I-<n> F-<k> fixed|accepted "<reason>"` (`APPROVE-OPEN`).
## B180 One-way doors one at a time
- AC-1 `approve` with two or more one-way doors is refused (`APPROVE-BULK`). Each one-way door is shown with its options, findings and facts before it is stamped ([0015](../decisions/0015-one-way-doors-are-approved-one-at-a.md)).
## B181 Typed references and a reading budget
- AC-1 A decision's `facts` and `supersedes` must resolve to a doc of the right type (`DOC-REF`); requirements and depends keep their own checks (`PLAN-REQ`, `PLAN-DAG`).
- AC-2 The card lists only the docs its text and references resolve to, as before; backlinks in the indexes stay an idea for [Later](later.md).
