# Goal
A project built as vertical slices with layers inside each slice keeps that shape: a slice owns its data and its internals, slices never depend on each other in a circle, and a generated map shows the structure (owner, 2026-10-24: "one slice never directly calls the internal database layer of another slice").

## U86 Data ownership
The owner's rule (2026-10-24): one slice never calls another slice's database layer directly; slices talk through interfaces, events or shared domain services ([Data ownership](../design/data-ownership.md)).
- AC-1 With `architecture.data`, the gate and `check --ci` fail (`ARCH-DATA`) a data edge from outside the owning module, a data node with no owner and not shared, and a node two modules claim; an approved `except` decision covers the edges it lists.
- AC-2 The card lists the data the unit's modules own and the shared data, and how to reach other data.
## U87 Module surfaces and cycles
The owner's go (2026-10-24) on the rest of the vertical-slice-with-layers pattern ([Module surfaces and cycles](../design/module-surface.md)); layers inside a slice use boundaries as they are. The CLI budget goes to 3,700 lines for U86 and U87.
- AC-1 A module with `api` fails `ARCH-API` on an edge from another module to its paths outside `api`; an approved `architecture.api.except` decision covers the edges it lists.
- AC-2 With `architecture.acyclic`, module edges that form a circle fail `ARCH-CYCLE`, once per set of modules; module edges an approved decision lists are left out.
## U88 Codebase map
The owner (2026-10-24): keep a tree in the project's docs that shows the structure of the codebase ([Codebase map](../design/codebase-map.md)).
- AC-1 `aidlc map` writes `<bundle>/codebase-map.md`: the module folders as a tree with each module's data and public paths, top-level folders no module covers, and module dependencies from the graph as a Mermaid flowchart and a table; an unchanged body is not rewritten; `map: false` turns it off.
- AC-2 Merge writes it with the indexes, so the merge commit carries it.
## U89 Plan-wide findings per file
From the first migration (2026-10-24): `aidlc check` on I-3's unit files passed and `next` asked for approval, but I-3's `PLAN-SLICE` showed only in a full check, and failed a later merge.
- AC-1 `check <files>` also reports the findings on the intents of the units among them; `approve` refuses a doc with a `PLAN-DECISION` or `PLAN-SLICE` finding on it or, for a unit, on its intent.
## U90 Codebase map in small pages
From the first migration (2026-10-24): the project's docs check refused the 7,600-char map (4,000 cap, a `**TL;DR:**` line per doc). The CLI budget goes to 3,800 lines.
- AC-1 The map is a tree page and, with a graph, a diagram page and a table page, linked to each other, each opening with a `**TL;DR:**` line; merge writes all three.
## U91 Deploy on the existing platform
From the first migration (2026-10-25): a deploy unit planned its own Argo CD Application, pull secret and names while a sibling infra repo already defined them; the replan came after the unit stopped ([Operations](../design/operations.md)).
- AC-1 With `deploy` in the profile and no `deploy.platform`, plan lint fails each intent that ships (`PLAN-PLATFORM`); `[]` passes.
- AC-2 A standard card lists the `deploy.platform` refs and says to build on them.
## U92 Approved docs within the project's caps
From the first migration (2026-10-25): a unit doc passed at 3,990 chars, its approval stamps took it to 4,019, and the project's own docs check (4,000 cap for every type) failed it; the plugin counted 12,000 for a Unit ([OKF validation](../design/okf-validation.md), [Approvals](../design/approvals.md)).
- AC-1 `docs.caps` sets size caps by type, with `default` for the types it does not name; `check`, the gate and the write hook use them.
- AC-2 `approve` refuses a doc its stamps would take over its cap, naming how much to trim, and writes nothing.
## U93 Verdicts newer than the report
From the first migration (2026-10-25): after a `GATE-PROOF` refusal the builder reported new mutations; `next` asked for a review, but the merge passed on verdicts that never saw them. `report` also called a unit that changes code "a unit that changes only tests" ([Gate](../design/gate.md), [Back-fill](../design/backfill.md)).
- AC-1 The gate counts a verdict only for the current diff and when newer than the last report, as `next` does.
- AC-2 `report` refuses a code unit's partial mutations in words that say it is proved by them instead of by revert.
## U94 Guard only this project's repository
From the first migration (2026-10-25): the lead's push of the infra repo's `main` was refused as a raw push of the project's base ([Hook mechanics](../design/hooks.md#wiring)).
- AC-1 A git call that `cd` or `-C` takes into another repository, sharing no remote or path with the project and holding no profile, passes the guard; one in a clone of the project, or naming its URL, does not.
## U95 Naming rules
The owner (2026-10-25), after two deploy stops on naming mismatches: a naming improvement for any project ([Naming rules](../design/names.md)).
- AC-1 With `names`, the gate fails an added line whose name, taken by a rule's `find` in its `files`, does not match its `pattern` (`GATE-NAME`); `check` fails a malformed rule.
- AC-2 The card lists the rules whose files overlap the unit's scope.
## U96 Naming through the lifecycle
The owner (2026-10-25): one naming convention through the whole lifecycle of the codebase ([Naming rules](../design/names.md#lifecycle)).
- AC-1 A `names` rule without `find` checks the path of each file a unit adds or renames under its `files` (`GATE-NAME`).
- AC-2 `init` ships a naming decision template with a section per stage; with `modules` and no `names` rule, `check` warns `PROFILE-NAMES`.
- AC-3 The card's names section tells the builder to use the decision's vocabulary, which the reviewer checks.
## U97 Upgrade names its new findings
From the first migration (2026-10-25): the 0.101.0 pin added a `PROFILE-NAMES` warning, a project test wants no profile finding, and every merge failed until a fix unit landed ([Vendoring](../design/vendoring.md)).
- AC-1 `upgrade` lists the findings `check` reports with the new copy and not with the old one.
## U98 Current dependencies
The owner (2026-10-25), on the first migration's open Dependabot advisories: latest packages and security patches are a permanent rule of the method, looked up by research since models are out of date ([Current dependencies](../design/dependencies.md)).
- AC-1 A card whose scope overlaps `deps.manifests` says to take versions from the registry; `report` refuses a manifest change without `deps` sources.
- AC-2 `deps.check` runs at the gate and in `check --ci`; the CI template runs daily; the constitution has the rule.
## U99 Profile units mutate the profile
From the first migration (2026-10-25): a unit whose AC is a profile setting counted as tests-only, and its only valid mutation was in the vendored CLI ([Back-fill](../design/backfill.md)).
- AC-1 `report` accepts a mutation of `.aidlc/profile.json` even when the unit's diff changes it.
## U100 Research holds on decisions
From the second project (2026-10-25): a research hold on decision 0003 (which MTA core) was recorded, but `aidlc research 0003` found no question and `next` skipped it ([State](../design/state.md)).
- AC-1 A decision held with `research:` gets a brief from `aidlc research <number>`, and `next` asks for its researcher until a digest answers it.
## U101 Decisions before units

## U102 Research holds on any doc
From the second project (2026-10-25): research holds on design docs (a capability catalogue) were recorded but not found by `research` or `next` ([State](../design/state.md#next)).
- AC-1 A research hold on any doc in the bundle gets a brief by the doc's name and holds `next` until answered.
