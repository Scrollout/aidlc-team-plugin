# Goal
Both projects build vertical slices that ship to dev one by one, every card says what it is and why with a path for everything it names, and a repeated call never changes the record. Each unit here came from steering both projects, from the drift found on 2026-10-25 on, shipped the day it was found ([Log](../log.md)).

# Units
## U117 Every slice cut before an intent is done
The owner (2026-10-25) asked whether both projects still build vertical slices end to end without drift: the first migration's I-3 counted as released after 2 of its 4 slices, as they shipped no product file, and its data ownership never reached the gate ([Grid](../design/grid.md#slices)).
- AC-1 An intent with a `# Slices` line naming no unit is not merged or released while its units are merged; `next` asks to cut that slice's units.
- AC-2 The intent template has a `# Slices` section.
## U118 Slices stay vertical
The owner (2026-10-25), high priority: prevent and fix the drift of both projects from vertical end-to-end slices. The second project cut its intent as layers with the walking skeleton behind them; the first project's portal and identity slices waited behind dependency and renaming fix units, chained only because `PLAN-SCOPE` demanded a `depends` for any shared file ([Grid](../design/grid.md#slices), [Plan lint](../design/plan-lint.md)).
- AC-1 `PLAN-SLICE` reports an intent with more live units than `plan.sliceUnits` without `# Slices`, a live unit on no slice line, a slice whose units have no top-level AC, a slice wider than `plan.sliceUnits` (default 3), and a unit waiting on a later slice.
- AC-2 `PLAN-SLICE` reports a unit of an intent waiting on a fix unit not yet merged.
- AC-3 `PLAN-SCOPE` asks for `depends` only between overlapping units of one intent; `next` never starts a unit whose scope overlaps one started and not merged, and puts intent units before fix units at the same priority.
## U119 The card cap counts lines
The owner (2026-10-25): budget the cards to 100 lines instead of chars. The second project's U-2 passed `check` while `card` refused it: PLAN-CARD sized only unapproved units, and a char cap pushed the lead to squeeze wording ([Unit card](../design/unit-card.md)).
- AC-1 The card cap is 100 lines; `card`, PLAN-CARD and the budget test count lines.
- AC-2 PLAN-CARD sizes every unit not yet merged, approved ones too.
## U120 A pipe after cd keeps the folder
`cd ~/platform-infra && git push -q origin main 2>&1 | tail -3` was refused as a raw push of the base, because any pipe or `||` in the command voided every `cd` ([Hooks](../design/hooks.md#wiring)).
- AC-1 A `cd` is unresolved only in a command with a subshell or when the `cd` itself sits in a pipeline or background job; a pipe or `||` after it keeps its folder.
## U121 Each slice ships to dev
deploy steps ran once per merged intent, so its 8 slices would reach dev only after the last one merged ([Deployment and operation](../design/operations.md)).
- AC-1 An intent with `# Slices` whose newest merged slice is not in its last passing release runs the deploy check, the owner's release and smoke while its next slices build; `deploy` and `release` accept it.
- AC-2 An intent is released only by a release whose base holds every merge.
- AC-3 While builders run, `next` names a due release step instead of waiting.
## U122 A built slice names its merged units
I-1, done before slice lines named units, came back ahead of I-5 with `next` asking to cut units for slices long built ([Grid](../design/grid.md#slices)).
- AC-1 The cut-slices line also asks to name the merged units that already built a slice.
## U123 A slice ships only its intent's units
after I-2's release, `next` offered a release of draft I-7, which has no units, because its slice line cites I-3's merged U-19 ([Deployment and operation](../design/operations.md)).
- AC-1 A slice is due to ship only from merged units of its own intent; a cited unit of another intent counts for nothing.
## U124 A manifest edit asks for sources only for a pin
listing the Makefile, CI workflow and deployment files that pin images in `deps.manifests` would make every edit to them need a sourced dep ([Current dependencies](../design/dependencies.md)).
- AC-1 `report` asks for `deps` only when the diff adds a line matching `deps.pin` to a manifest.
## U125 Each reviewer in flight is waited for
the security review recorded its pass while the general review still ran, and `next` asked for the general review again ([In flight](../design/in-flight.md)).
- AC-1 The reviewing mark counts the reviewers launched; `review record` removes one, so `next` waits while any is in flight.
## U126 The intent is the vertical spec
From the AI-DLC guidance on spec architecture the owner brought (a talk, 2026-05; owner, 2026-10-26): vertical specs first, horizontal ones extracted on reuse, the why beside each rule; the grid named `capabilities/` docs nothing writes ([Grid](../design/grid.md)).
- AC-1 The intent template has `# Risks` and asks each slice's rule or limit for its why; the grid names the intent as the vertical spec and extracts horizontal docs on a second use.
## U127 The card shows what a name rule finds
the card rendered a banned-word rule as `(?!)`, so neither builder nor reviewer saw the words, and the merge gate refused `/var/spool/postfix` ([Naming rules](../design/names.md)).
- AC-1 Each name rule on the card shows its `find`; one whose pattern is `(?!)` reads as "nothing may match" its `find`.
## U128 The card names its slice, its why and every reference
a card names sources with no path, does not say whether the unit is a vertical slice or horizontal work, and carries no business reason ([Unit card](../design/unit-card.md)).
- AC-1 The card's `Spec:` line names the unit's slice and intent path, vertical with a top-level AC, horizontal without one or with no intent.
- AC-2 The card carries the unit's `# Why`, its interface lines as written with each link's path, and `## References` for each intent, unit, requirement or decision the text names, with its path.
## U129 A release ships a green base
`next` offered the owner's release on a base 11 merges ahead of its remote whose CI had failed every run ([CI on the base](../design/base-ci.md)).
- AC-1 With `ci.wait`, `next` asks for the push and the CI wait before the release prompt, waits on a red base, and `release` refuses a base not pushed or not green.
## U130 A fix round at work is waited for
with the security focus's pass kept, `next` asked for a general review while the fix-round builder still committed ([In flight](../design/in-flight.md)).
- AC-1 A builder launched after the last verdict and the last report, its heartbeat fresh, makes the unit building whatever verdict a focus kept.
## U131 The Spec line names its evidence
a vertical or horizontal label that reads no evidence can contradict the card; make it precise and deterministic ([Unit card](../design/unit-card.md)).
- AC-1 The card's Spec line comes from the function `PLAN-SLICE` uses and names its evidence: the top-level ACs that prove a vertical unit, the vertical units that need a supporting one.
- AC-2 `PLAN-SLICE` reports a unit on a slice with a vertical unit that no vertical unit of the slice depends on.
## U132 Dependency tests stay offline
two units tested "each pin is the newest" in the unit level, which needed the network and would turn every branch red on an upstream release ([Current dependencies](../design/dependencies.md)).
- AC-1 The card's Dependencies section says the live currency and advisory checks are `deps.check`, and a unit's test proves a check on fixed inputs offline.
## U133 A retried verdict counts once
From the owner's architecture review (2026-10-26, idempotency): a reviewer's retried `review record` appended a second round and could spend a fix round or escalate; a retried release reruns `deploy.run` ([Review rounds](../design/review-rounds.md), [Operations](../design/operations.md)).
- AC-1 The same verdict and findings for the same diff with no report in between replace their round.
- AC-2 Operations says `deploy.run` must be safe to run twice on one base.
## U134 Docs, diagrams and the pipeline aligned
once the day's units were in, align the docs, the diagrams and the tree, and clean the noise ([Pipeline](../design/pipeline.md), [Slices](../design/slices.md)).
- AC-1 A pipeline page lists every stage in order; a slices page holds the plan rules, the Spec line and the slice release, and the oversized design docs fall under their caps.
- AC-2 The README, grid, overview and intent-state diagrams show slices, risks, the Spec line, reviews per focus and the CI wait before a release; M12 closes at U122 and M13 holds the rest.
## U135 Level paths name test files
with `test/e2e/**` as the e2e level's paths, a harness-only fix unit had no code to revert and no file a mutation could name ([Profile](../design/profile.md)).
- AC-1 The profile doc says `paths` name the test files, never a folder holding helpers, which are code the proof reverts.
## U136 Name neutral docs
a design doc headed a section with a vendor's name; the public repo names no vendor or product, only what it calls.
- AC-1 No vendor or product name in the docs' prose, headings, source titles or examples; no vendor source URL either; a test fails on a listed name anywhere in them.
## U137 Init writes the Dependabot config
a Dependabot file added beside init's files was flagged `CI-COMMIT` on the first run, and every project wants bumps from day one ([Current dependencies](../design/dependencies.md)).
- AC-1 `init` writes `.github/dependabot.yml` for the workflow actions, among the files a direct commit may carry.
## U138 AGENTS.md names the root index
the AGENTS.md init writes said "read an index, then one doc" without naming the bundle's root `index.md`, the OKF entry point, so an agent had no first page ([Profile and templates](../design/profile.md)).
- AC-1 The AGENTS.md template's first docs pointer is `<bundle>/index.md`, read first, then the folder's index, then one doc.
## U139 Decisions take shape with the intent; no vendor left
a new project's intent sat in elaboration with no decision drafted, and the OKF design docs still named a vendor and its repository ([State](../design/state.md), [OKF](../design/okf.md)).
- AC-1 While a draft intent with open points links no decision, `next` asks the lead to draft the decisions it needs, linked from it, as the owner answers.
- AC-2 No vendor name or vendor URL in the docs, the name-neutral test covering them.
## U140 Project checks on every merge
CI's linter went red on the base, because the gate ran only the touched modules' checks and the test levels ([Profile and templates](../design/profile.md)).
- AC-1 The profile's `checks` run on every trial merge as `GATE-CHECK`, whatever the unit touches, and the card lists them.
## U141 A stop holds back no other unit
The prompt eval (2026-10-26): `next` kept naming one unit's stop, an owner question, ahead of another unit's review, so the back-fill never merged ([State](../design/state.md)).
- AC-1 A gated, escalated or stopped unit comes after the other units' review, fix round and restart.
